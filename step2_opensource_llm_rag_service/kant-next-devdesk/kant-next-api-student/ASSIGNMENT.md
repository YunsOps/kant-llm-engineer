# KANT NEXT DevDesk: 공개 자료를 수집하는 질문 API

KANT NEXT 개발지원팀은 DevDesk가 공개 릴리스 자료를 근거로 답하도록 개선하려고 합니다. 자료를 모아 문서로 정리하고, 다른 서비스가 문서를 조회하거나 질문할 수 있는 API를 구현하세요.

**필수 4문제와 선택 심화 1문제**입니다. 필수는 `app.py`의 `support.todo("수집: 페이지와 크기")` 같은 부분을 조건이나 값으로 바꿉니다. 반복문, 파일 저장, 오류 처리와 비동기 실행 순서는 제공합니다. 함수의 주석을 읽고 **정상 입력 → 오류 입력 → 기능 검사** 순서로 진행하세요.

| 문제 | 완성할 기능 |
|---|---|
| 필수 1. 공개 자료 수집과 저장 | 페이지를 따라 자료를 모아 원본과 수집 결과 저장 |
| 필수 2. 품질 점검과 문서 구성 | 채택할 자료를 골라 문서로 정리 |
| 필수 3. 문서 API | 문서 등록과 조회, 입력과 응답 검증 |
| 필수 4. 질문 API | 모델 연결, 실패 처리, 요청 제한과 기록 |
| 선택 심화 1. 문서 변경 내역 | 두 시점의 스냅샷 비교 |

수집, 정제, 조회, 재시도 함수의 `작성 메모`에는 구현 이유를 각각 1~2줄로 남깁니다. API를 사용하는 이유, 본문과 메타데이터를 구분한 이유, HTTP 오류의 차이, 비동기 대기와 재시도 상한을 자기 코드에 연결해 설명하세요. 실행과 제출 명령은 [시작 안내](README.md)에 있습니다.

현재 문제의 작성할 함수를 구현한 뒤 기본 실행, 결과 확인, 기능 검사 순서로 진행합니다. 명령의 의미와 생성되는 파일은 [시작 안내](README.md)의 `명령어를 읽는 방법`과 `실행 후 무엇을 확인하나요?`에서 확인하세요. `data/`는 제공 입력, `artifacts/`는 본인이 실행한 결과이며 결과 파일은 제출하지 않습니다.

## 필수 1. 공개 자료를 모아 다시 읽을 수 있게 저장하기

GitHub의 `astral-sh/uv` 공개 릴리스를 수집해 다시 읽을 수 있게 저장하세요.

**작성할 함수:** `collect_releases`의 페이지, 상태 확인, 다음 페이지 조건과 저장할 값. [공식 API 설명](https://docs.github.com/en/rest/releases/releases#list-releases)에서 요청 주소, 파라미터, 응답 필드와 호출 제한을 확인합니다.

- GET `https://api.github.com/repos/astral-sh/uv/releases`를 사용합니다.
- `page=1`부터 시작하고 기본값은 `per_page=5`, `max_pages=2`입니다.
- `response.links`에 `next`가 없으면 종료합니다. 다음 페이지가 남아 있는데 상한에 도달하면 `limited=true`입니다.
- HTTP timeout을 지정하고 상태, JSON 파싱, 최상위 배열을 확인합니다. 오류가 나면 재시도하거나 건너뛰지 않고 중단합니다.

제공된 저장 반복문에서 현재 값을 UTF-8 JSON으로 기록하세요. `raw_pages.json`에는 성공한 페이지의 원본 객체를, `collection_report.json`에는 이번 실행의 성공 여부, 페이지와 행 수, 실패 페이지를 남깁니다. 성공한 부분이 있더라도 실패한 실행은 정제에 사용하지 않습니다. 이전 성공 파일을 재사용하지 않는 처리도 제공됩니다.

| 입력 | 기대 결과 |
|---|---|
| 1페이지에 next가 있고 2페이지에 없음 | 2페이지 저장, success=true, limited=false |
| 2페이지에도 next가 남음 | 2페이지 저장, success=true, limited=true |
| 1페이지 성공 후 2페이지가 503 | 첫 페이지만 저장, success=false, failed_page=2 |

**확인:** 저장 파일을 다시 읽어 구조와 건수를 비교합니다. `check collect` 뒤 `run collect --live`로 실제 수집도 확인하세요. 최대 두 페이지는 전체 릴리스 이력이 아닙니다.

## 필수 2. 믿고 사용할 문서로 정리하기

수집한 행을 채택, 격리, 제외로 나누어 사용할 문서를 만드세요.

**작성할 함수:** `normalize_releases`의 자료형과 빈 본문 검사, 제목 대체, 중복 판단과 문서 값. HTML 정리, URL과 날짜 문법 검사, 반복과 파일 저장은 제공합니다. 분류 순서는 다음과 같습니다.

1. 객체, 양의 정수 ID와 boolean 플래그인지 확인합니다.
2. `draft=true` 또는 `prerelease=true`는 제외합니다.
3. 제목, 본문, URL, 게시시각의 형식과 길이를 확인합니다.
4. 이미 채택한 ID는 격리합니다. 잘못된 첫 행이 뒤의 정상 행을 막으면 안 됩니다.
5. 통과한 값으로 새 문서를 만듭니다. 원본 객체는 수정하지 않습니다.

| 입력 | 기대 결과 |
|---|---|
| name이 공백이고 tag_name이 v-check | 제목을 v-check로 채택 |
| 같은 ID의 첫 행은 본문이 숫자, 다음 행은 정상 | 첫 행 격리, 다음 행 채택 |
| 초안이며 본문이 비어 있음 | 내용 검사보다 범위 판단을 먼저 하므로 제외 |

`clean_text`는 제목과 본문의 태그와 공백을 정리합니다. `validate_url`이 반환한 앞뒤 공백 없는 URL을 사용하세요. 게시시각은 원본 기록에 보존하고 문서에는 별도의 수집시각을 넣습니다.

### 문서 데이터 형식

정제 결과와 API가 같은 여섯 필드를 사용합니다. 문자열은 앞뒤 공백을 정리한 뒤 길이를 확인하며 숫자를 자동으로 문자열로 바꾸지 않습니다. 추가 필드는 허용하지 않습니다.

| 필드 | 조건 |
|---|---|
| `doc_id` | 영문, 숫자, 하이픈, 밑줄 1~100자. 정책은 `policy-*`, 수집 문서는 `release-uv-{id}` |
| `title` | 문자열 1~300자 |
| `body` | 문자열 1~20,000자 |
| `source_url` | HTTP(S) URL 1~2,048자, host 필수. 내부 공백 금지 |
| `collected_at` | UTC ISO8601 문자열 |
| `category` | installation, access, incident, general, release 중 하나 |

`normalize_releases`는 `documents`, `quarantine`, `excluded`, `quality_report`를 가진 dict를 반환합니다. 제공 실행부가 같은 이름의 JSON 파일을 저장합니다. 원천 필드별 규칙, 사유 코드와 저장 형식은 [제공 자료 설명](data/DATA_CARD.md)에 있습니다.

**확인:** `run documents`와 `check documents`로 확인합니다. 고정 입력 10건은 채택 3건, 격리 5건, 제외 2건입니다. 채택 ID는 `release-uv-101`, `release-uv-102`, `release-uv-109`입니다. 같은 입력과 시각에는 같은 결과가 나와야 합니다. 실제 수집 자료에도 같은 정제 규칙을 적용하되 이 건수와 ID를 고정 정답으로 쓰지 않습니다.

## 필수 3. 다른 프로그램이 사용할 문서 API 만들기

문서를 등록하고 조회하는 API를 완성하세요.

**작성할 부분:** `Document`, `QueryRequest`, `QueryReply`의 예시 아래에 모델 필드 9개를 선언하고, 각 검증 함수의 `support.todo` 한 줄을 지웁니다. `find_document`, `register_document`, `response_models`에는 없는 ID, 중복 등록 조건과 응답 모델을 채웁니다. 공백, URL, 날짜와 중복 목록의 검사 틀 및 서버 연결은 제공합니다.

| 요청 | 정상 | 오류 |
|---|---|---|
| GET /health | 200, status/mode/document_count | 현재 메모리의 문서 수 |
| GET /documents | 200, Document 배열 | 빈 목록도 정상 |
| GET /documents/{doc_id} | 200, Document | 없는 ID는 404 |
| POST /documents | 201, 등록한 Document | 같은 ID 또는 URL은 409, 형식 오류는 422 |
| POST /query | 200, QueryReply | 문서 API만 실행하면 501. 필수 4에서 완성 |

POST는 위 여섯 필드를 모두 받습니다. 다음 문서로 등록과 조회를 확인하세요.

```json
{
  "doc_id": "manual-api-guide",
  "title": "API 사용 문의 안내",
  "body": "API 사용 문의에는 요청 경로와 오류 상태를 적습니다.",
  "source_url": "https://devdesk.example.invalid/manual/api-guide",
  "collected_at": "2026-09-21T00:00:00Z",
  "category": "general"
}
```

처음에는 정책 6개를 읽으며 정상 fixture 정제 후에는 총 9개입니다. 현재 모드의 수집 결과가 있다면 정제까지 완료해야 서버를 시작할 수 있습니다. 제공 실행부가 실패한 수집, 오래된 정제 파일과 중복 자료를 확인합니다. POST 등록은 메모리에만 남으므로 재시작하면 사라지며 이 동작은 `/docs`에 표시됩니다.

**확인:** `serve --stage document-api`와 `check document-api`를 실행합니다. 정상 등록과 조회 뒤 같은 문서를 다시 등록해 409인지 확인하세요. `manual/a` 같은 잘못된 ID는 422입니다. 누락, 자료형, 빈 값과 `/docs`의 스키마도 대조하고 직접 선택한 경계값 하나의 요청과 응답을 보관합니다. 빈 저장소 검사는 제공되므로 정책 파일을 지우지 않습니다.

## 필수 4. 질문 API에 LLM을 연결하고 실패 처리하기

질문과 선택 문서를 모델에 전달하고, 실패나 과도한 요청을 처리하는 API를 완성하세요. 아래 **모델 연결, 실패 처리, 요청 제한과 기록을 모두 구현**해야 필수 4가 완료됩니다. 소제목은 한 문제 안에서 구현할 기능입니다.

### 모델 연결

**작성할 함수:** `build_prompt`에서 질문과 문서를 dict에 담고, `call_model_once`에서 응답 JSON과 출처를 검사하세요. HTTP 요청과 `await`, 모델 API 요청 형식은 제공합니다.

| 요청 필드 | 조건 |
|---|---|
| `question` | 공백 정리 후 문자열 3~1,000자 |
| `document_ids` | 필수. 서로 다른 DocumentId 1~3개 |
| `session_id` | 기본 demo, 공백 정리 후 문자열 1~64자. 대화 이력은 저장하지 않음 |

DocumentId는 위 `doc_id`와 같은 문자와 길이 규칙입니다. 추가 필드나 형식 오류는 422이고 없는 ID는 모델 호출 전 404입니다. `GET /documents`에서 ID를 골라 요청하세요. 선택 문서의 실제 본문과 메타데이터만 모델에 전달하며 검색이나 자동 문서 선택은 구현하지 않습니다.

`POLICY_INSTRUCTIONS`에는 기본 B1 지침이 있습니다. 이전 과제의 지침을 사용한다면 역할과 근거 확인 기준만 옮기세요. 문서 6개가 포함된 이전 `system_prompt.txt` 전체를 붙이지 않습니다.

| 답변 필드 | 조건 |
|---|---|
| `answer` | 공백 정리 후 비어 있지 않은 문자열 |
| `source_ids` | 중복 없는 DocumentId 배열. 현재 선택 문서에 있는 ID만 허용 |
| `needs_human` | boolean. 문자열 false, 숫자 0/1은 거부 |
| `category` | installation, access, incident, general 중 하나 |

출처가 비면 `needs_human=true`여야 합니다. 담당자 확인이 필요한 정상 답변은 200이며 모델 장애를 이런 답변으로 바꾸지 않습니다.

**확인:** `run query`와 `check query`로 정상 응답을 먼저 확인한 뒤 잘못된 JSON, 자료형, 선택하지 않은 출처를 거부하는지 검사하세요. 실제 모델 답변은 선택 문서와 직접 대조합니다.

### 실패 처리

**작성할 함수:** `query_with_retry`에서 재시도 조건 두 개와 공급자 429의 응답 상태를 채우세요. `attempt`는 첫 시도에서 0, 두 번째에서 1입니다. 반복, 비동기 대기, HTTP timeout과 한 시도 전체의 제한 시간은 제공합니다.

| 상황 | 최종 응답 | 모델 호출 |
|---|---|---|
| 정상 | 200 | 1회 |
| 첫 timeout 또는 5xx 뒤 성공 | 200 | 2회 |
| timeout 두 번 | 504 | 2회 |
| 5xx 두 번 | 502 | 2회 |
| 공급자 429 | 503 | 1회 |
| 다른 4xx, 연결/JSON/스키마/출처 오류 | 502 | 1회 |
| 재시도 후 다른 실패 | 마지막 실패 종류의 위 오류 | 2회 |
| live 키 미설정 | 503 | 0회 |

**확인:** `check retry`에서 503 뒤 성공하면 두 번, 401이면 한 번만 호출하는지 확인합니다. 오류는 제공된 짧은 설명으로 반환하고 원문 예외나 키를 노출하지 않습니다. 실패는 고정 응답으로 검사하며 실제 모델에 고의로 장애를 일으키지 않습니다.

### 요청 제한과 기록

**작성할 함수:** `admit_query`에서 시간 구간 갱신, 한도 초과와 요청 수 증가를 채우고, `request_logging`에서 로그 필드를 작성하세요. 서버 연결과 미들웨어의 `await call_next`는 제공합니다.

- `POST /query`만 단일 프로세스 전체 30회/60초로 제한합니다. 모든 호출자가 한도를 공유합니다.
- 형식과 문서 ID를 먼저 확인합니다. 422/404는 횟수에 포함하지 않습니다.
- `admit_query`는 허용이면 0, 초과이면 남은 초를 올림한 양의 정수를 반환합니다. 초과 응답은 429와 `Retry-After`이며 모델을 부르지 않습니다.
- 구간이 끝나면 횟수를 초기화합니다. 상태 갱신은 await 전에 끝내며 모델 재시도는 추가로 세지 않습니다.
- 로그에는 method, 경로 양식, status, mode, elapsed_ms만 넣습니다. 경로는 `support.safe_route(request)`를 사용하고 응답에는 `X-DevDesk-Mode`를 설정합니다.

검사에서 limit=2, window=10이면 0초와 1초는 허용, 2초는 거부, 10초는 새 구간입니다. 질문, 본문, 인증 헤더와 원문 예외는 로그에 넣지 않습니다.

**확인:** `serve`와 `check observe`로 제한과 회복, 차단 시 모델 호출 0회, 안전한 로그를 검사합니다. 제공 검사는 고정 지연 요청 3개의 대기가 겹치는지도 확인합니다. 운영 규모의 부하 시험이나 분산 환경 검증은 포함하지 않습니다.

## 선택 심화 1. 두 시점의 문서 변경 내역 제공하기

두 시점의 문서에서 무엇이 바뀌었는지 확인하는 기능을 만드세요.

**작성할 함수:** `compare_snapshots(before, after)`의 자료구조와 처리 순서부터 직접 구성합니다. 같은 범위의 전체 스냅샷 두 개와 `GET /document-changes` 연결은 제공합니다.

- ID별로 `added`, `changed`, `unchanged`, `missing`을 구분합니다.
- `title`, `body`, `source_url`, `category`의 변경 필드를 `changed_fields`에 담습니다. 추가와 부재는 빈 배열입니다.
- 수집시각만 바뀌면 unchanged입니다. 입력은 수정하지 않고 결과를 doc_id 순서로 정렬합니다.
- 빈 입력, 입력 순서 변경, 한 문서의 여러 필드 변경을 처리합니다. missing은 비교 자료에 없다는 뜻이며 실제 삭제를 뜻하지 않습니다.

`challenge`와 `check challenge`로 별도 실행합니다. 이 함수를 완성하지 않아도 필수 검사와 서버가 실행됩니다.

## 제출

과제 제출 시스템에는 다음 두 파일만 제출합니다.

1. `app.py`: 구현 코드와 지정된 위치의 짧은 이유 또는 관측 주석
2. `AI_USAGE.md`: AI 사용 기록. 사용하지 않았다면 `사용하지 않음`으로 기록

`data/`는 제공 입력이고 `artifacts/`는 실행 결과를 직접 확인하는 폴더입니다. 두 폴더와 `support.py`, `checks.py`, 환경 설정 파일은 제출하지 않습니다. `.env`, `.venv`, 캐시, 실제 키와 개인 정보도 포함하지 않습니다. 실행 결과를 확인하는 과정은 과제에 포함되지만, 제출 파일은 위 두 개로 충분합니다.

외부 연결이 막혔다면 오류를 확인하고 운영자에게 문의합니다.
